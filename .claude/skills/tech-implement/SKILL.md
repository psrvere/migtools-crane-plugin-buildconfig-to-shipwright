# /tech-implement — Implement a Triaged Migration Issue

You are a senior engineer implementing an issue that `/tech-design` has already researched.
The design doc carries the evidence; your job is to plan, implement, test, review, and ship
the change without re-litigating research that is already done.

## Arguments

The user invoked this with: $ARGUMENTS

Must match `BUILD-XXXX`. Find the design doc at `<Designs Directory>/BUILD-XXXX-*.md`.
If none exists, stop and tell the user to run `/tech-design BUILD-XXXX` first. Implementing
without a design doc is how unresearched assumptions reach a PR.

## Iron Law

- **Never push to `origin`.** `origin` is the shared upstream org repo. Branches go to the
  fork remote, and changes reach upstream only through a PR.
- **Never work in the user's checkout.** Use a git worktree — see **Isolation** below.
- **Never edit the operator's strategy files.** They are generated. Strategy changes go to
  the Strategy Catalog Repo.
- **Never edit the Crane Lib Repo.** It is frozen prior art, not a PR target.
- **One branch = one story.** Never add a commit for a different BUILD key to this branch.
- **No status claim without a results file.** See the Phase 7 status gate.

## Repo & Tool Map

**All local paths come from `repo.md` at the project root. Never hardcode a path.**

If `repo.md` does not exist, invoke `/setup-repos` and stop until it does.

Throughout this skill, `<Label>` means the path stored under that label in `repo.md`.
`/tech-design` documents the full repo map; this skill only names where changes are *made*:

| Label | Role in implementation |
|-------|------------------------|
| Crane Plugin Repo | **The conversion code.** `buildconfig/` — the usual PR target |
| Strategy Catalog Repo | **The PR target for every ClusterBuildStrategy change** |
| Crane Repo | CLI convert subcommand, when the issue touches CLI behaviour |
| Upstream Shipwright Build Repo | API type changes, upstream proposals |
| Downstream Operator Repo | **Read-only.** Its `config/shipwright/build/strategy/*.yaml` are generated by `make strategy-catalog` |
| Crane Lib Repo | **Read-only.** Frozen archive; prior art to port, never a PR target |

The conversion code moved out of crane-lib on 2026-08-13. A design doc that points at
`convert/buildconfigs.go` is describing the archive; the live file is
`<Crane Plugin Repo>/buildconfig/converter.go`.

### Fork remote

Never assume a remote name — it differs per repo and per machine. Resolve it:

```bash
git -C "<repo path>" remote -v
```

`origin` is upstream. The fork is whichever other remote points at the user's own account.
If exactly one non-origin remote exists, use it. If there are none or several, ask which to
use and do not guess. Derive the fork owner for `gh pr create` from that remote's URL rather
than hardcoding a username.

## Isolation — required before any change

Another session may be using the same clone. Two sessions sharing one checkout share one
index and one HEAD, so a plain `git add` + `git commit` can commit another session's staged
files, on another session's branch, under your signature.

Work in a dedicated worktree, created outside the checkout so it does not appear as
untracked content:

```bash
CP="<Crane Plugin Repo>"                       # or whichever repo this issue changes
WT="$(dirname "$CP")/.bcshp-worktrees/$(basename "$CP")-BUILD-XXXX-<slug>"
git -C "$CP" fetch origin --quiet
git -C "$CP" worktree add -b "BUILD-XXXX-<slug>" "$WT" origin/main
```

Every command from here runs with `git -C "$WT"`. Never run `checkout`, `switch`, `pull`,
`merge` or `reset` in the user's own checkout.

When the work is merged, remove it: `git -C "$CP" worktree remove "$WT"`.

## Phase 0: Read the Design Doc, Validate Setup

1. Read and **validate** `repo.md`. Existence is not enough — a hand-edited file can still
   hold template placeholders.

   - If it is absent, invoke `/setup-repos` and stop.
   - If a required label is missing, or a path still contains `/path/to/`, or a configured
     path does not exist on disk, report exactly which entries are bad and stop with
     **BLOCKED**. Do not fall back to a guess.

   Required here: Crane Plugin Repo, Designs Directory. Strategy Catalog Repo is required
   for `buildah-flag` and `s2i-flag` issues. Everything else is optional, and its dependent
   steps are skipped when unset.

2. Read the design doc at `<Designs Directory>/BUILD-XXXX-*.md`.

   Then check that it reached a resolved state. `/tech-design` ends every doc it writes
   with a terminal sentinel; an unresolved doc is one whose own author flagged open
   questions, and starting implementation against it is how an assumption nobody
   confirmed reaches a PR.

```bash
sentinel="$(tail -1 "<the design doc>")"
case "$sentinel" in
  "NO UNRESOLVED MARKERS")
    ;;
  "UNRESOLVED MARKERS: "*)
    echo "BLOCKED: $sentinel — resolve them in the design doc first"; exit 1 ;;
  *)
    echo "NOTE: no terminal sentinel; this doc predates the current template. Proceeding." ;;
esac
```

   A doc with no sentinel predates the sentinel and is reported, not blocked, so
   in-flight work triaged under the previous template keeps running.

3. Read the current Jira state: `jira issue view BUILD-XXXX --plain --comments 5`.

4. Extract from the design doc frontmatter: **topic_class**, **ceremony_class**,
   **necessity**, **capability**. From the body: the **Files Reference** table and the
   **Proposed Change**.

   Read priority, story points, blockers and dependencies from **Jira**, not from the
   design doc. Jira owns story state; the design doc owns the design.

5. Check for existing work before creating anything. Remote-only branches count — a fresh
   clone has no local branches at all:

```bash
CP="<Crane Plugin Repo>"
git -C "$CP" fetch origin --quiet
git -C "$CP" for-each-ref --format='%(refname:short)' refs/heads refs/remotes \
  | grep -E "BUILD-XXXX" | sort -u
```

   If anything matches, **stop**. One branch per story is user policy. Resume that branch or
   get explicit approval to replace it; do not open a second one.

6. Search unmerged branches for work already in flight on this feature:

```bash
# --no-ext-diff: the repo's ext diff driver defeats grep-over-diff.
# origin/main: a stale local main misattributes already-merged work.
# Three dots, not two: `A..B` is a plain endpoint diff, so a branch that is merely
# behind main reports main's own content as a removal and matches every keyword.
# `A...B` diffs from the merge base and shows only what the branch itself added.
# Note: `2>/dev/null` also hides a real "unknown revision" (e.g. a force-pushed branch
# whose merge base was GC'd), which then reads as "no work found". If a branch you expect
# to match comes back empty, re-run its diff without `2>/dev/null` to tell the two apart.
git -C "$CP" for-each-ref --format='%(refname:short)' refs/heads refs/remotes/origin \
  | grep -vE '^(main|origin/main|origin/HEAD)$' | sort -u \
  | while read -r branch; do
      result=$(git -C "$CP" diff --no-ext-diff "origin/main...$branch" -- buildconfig/ 2>/dev/null \
               | grep -i "<feature-keyword>")
      [ -n "$result" ] && { echo "=== $branch ==="; echo "$result"; }
    done
```

   WIP branches may carry wrong assumptions. Verify param names match the actual strategy
   parameter, the approach matches the design doc, and tests assert the real param names.

Present a summary: "Implementing BUILD-XXXX. Design doc says: [summary]. Existing branches:
[none / list]. Ready to proceed?" Wait for the answer.

## Story Point & Estimation Scale

Used when setting Jira story points. Jira is the only source for points; the design doc
does not carry them, so there is nothing to reconcile.

| Points | Complexity | Est. Days | When to use |
|--------|-----------|-----------|-------------|
| 2 | Small, well-bounded | 2 days | Single repo change, clear pattern exists |
| 3 | Moderate | 3 days | Multi-repo change, conversion logic + tests |
| 4 | Large | 5 days | Cross-cutting, API changes, upstream proposals |

Minimum is 2. If something looks like 5+, flag it and propose a split.
**Est. Days = Points**, except 4 points = 5 days.

## Branch Naming

`BUILD-XXXX-<short-slug>` — e.g. `BUILD-1578-no-cache-buildah`. Created in Phase 0's
worktree command, from **fetched** `origin/main`, never from a local `main` that may be stale.

## Phase 1: Confirm Approach

The design doc already holds the research, so this is a confirmation, not a fresh
brainstorm. Confirm the approach still holds, agree the testing strategy, and note anything
that changed since the doc was written. `compound-engineering:ce-brainstorm` is available if
the scope turns out to be less settled than the doc implies.

## Phase 2: Plan

Use `EnterPlanMode`, or `compound-engineering:ce-plan`, to produce a plan covering the exact
files per repo, what changes in each, and the pattern being followed.

### Testing plan by classification

Select the strategy under test from the design doc's `topic_class` frontmatter field. A
`s2i-flag` issue tested against `buildah.yaml` produces a confidently wrong result.

| `topic_class` | Catalog path (the PR target) |
|---|---|
| `buildah-flag` | `clusterBuildStrategy/buildah/buildah.yaml` |
| `s2i-flag` | `clusterBuildStrategy/source-to-image/source-to-image.yaml` |
| anything else touching a strategy | every file under `clusterBuildStrategy/` |

**`buildah-flag` / `s2i-flag` / `field-mapping`** — unit tests in the Crane Plugin Repo
covering every `From` reference kind (ImageStreamTag, ImageStreamImage, DockerImage), error
cases (unknown kind, nil values), and exact param name and value assertions. Then a cluster
test, per the gotchas below.

**`crane-conversion` / `crane-cli`** — unit tests plus an end-to-end conversion of a sample
BuildConfig YAML, asserting on the emitted Shipwright resources.

**`api-change`** — Go tests in the Upstream Shipwright Build Repo, plus API compatibility
verification.

**`documentation` / `spike`** — no automated tests; manual review of the output.

Run tests with `GOWORK=off`. The workspace `go.work` resolves dependencies across modules,
while CI builds each repo standalone:

```bash
GOWORK=off go test ./... -count=1        # in the Crane Plugin Repo worktree
```

### Cluster testing gotchas

Hard-won from previous implementations. Apply them.

1. **Use OpenShift, not Kind.** The downstream buildah strategy pulls
   `registry.redhat.io/ubi10/buildah` (needs Red Hat pull secrets) and wants `SETFCAP`.
   Kind has neither.

2. **The operator reconciles the shipped strategies.** It owns `buildah` and
   `source-to-image` and will revert edits. To test a modified strategy, create a **new**
   one named for the issue — `buildah-BUILD-XXXX` — point the test Build at that name, and
   delete it when done.

3. **`docker-image://` prefix is required** when `--build-context` replaces a FROM image
   with a Docker image. `--build-context debian:slim=alpine:3.20` silently does nothing;
   `--build-context debian:slim=docker-image://alpine:3.20` works. The upstream
   multiarch-native-buildah strategy is missing this prefix — a latent bug.

4. **`FROM scratch` cannot be overridden.** `scratch` is a reserved keyword, so
   `--build-context scratch=...` has no effect. Test with a Dockerfile whose last `FROM` is
   a real image.

5. **Bind-mounting a secret-backed volume needs `:ro`.** Under `pipelines-scc`, an
   unprivileged buildah step fails at `RUN` with `remounting ... with flags [] instead of
   [ST_RDONLY]: permission denied` unless the mount flags match the read-only source. Use
   `--volume /etc/npm:/etc/npm:ro`.

6. **Compare image sizes, not just logs.** Build logs can still print the original FROM
   image name even when `--build-context` overrode it. Differing output image sizes are the
   definitive proof.

7. **Use a GitHub Gist for a test Dockerfile**, point the Build's Git source at it, and
   delete the gist afterwards.

8. **Installing operators changes the user's cluster.** If the Builds operator is absent,
   show the user the subscription manifests for OpenShift Pipelines and OpenShift Builds
   plus the `OpenShiftBuild` CR that enables Shipwright, and **ask before applying them**.
   Do not install onto a cluster unprompted.

## Phase 3: Implement

Order matters — a conversion that references a strategy parameter cannot be tested until
that parameter exists.

1. **Strategy Catalog Repo first**, if the issue changes a ClusterBuildStrategy.
2. **Crane Plugin Repo second** — the conversion logic in `buildconfig/`.
3. **Unit tests third.**
4. **Run them**: `GOWORK=off go test ./... -count=1`.

`compound-engineering:ce-work` is available for execution.

## Phase 4: Review

Run `compound-engineering:ce-code-review` over the change. If `/tech-review` is available on
this machine, run it too for the cross-repo checks. Neither ships with this repo, so note it
as SKIPPED in the Compliance Report rather than failing when absent.

## Phase 5: Test

If `/tech-test` is available, invoke it with `BUILD-XXXX` — it runs the classification-driven
unit and cluster tests, creates the custom strategy, verifies, and cleans up. It does not
ship with this repo; when it is absent, fall back to the Phase 2 testing plan and record the
substitution.

Record results to `<Designs Directory>/test-results/BUILD-XXXX-results.md` with the exact
commands, pasted raw output, exit codes, and the branch HEAD SHA they ran against.

## Phase 6: Commit & Push to the Fork

1. Confirm the worktree is on the story branch — never re-create it here:

```bash
git -C "$WT" branch --show-current        # must equal BUILD-XXXX-<slug>
```

2. Rebase onto fetched `origin/main`, inside the worktree, then re-run the tests:

```bash
git -C "$WT" fetch origin --quiet
git -C "$WT" rebase origin/main
```

   For a stacked branch, restack on the parent's **current** tip — a stale stack silently
   drops the parent's later fixes.

   If the rebase reports conflicts, **stop**. Do not commit or push a worktree that holds
   conflict markers. Either resolve them and `git -C "$WT" rebase --continue`, or
   `git -C "$WT" rebase --abort` and surface the conflict to the user for a decision.

3. Commit only your own paths. A shared index can hold another session's staged files, and a
   bare `git add .` would sweep them into your commit:

```bash
git -C "$WT" commit --only -s -S -m "[BUILD-XXXX] <type>: <subject>" -- buildconfig/converter.go buildconfig/converter_test.go
```

   List every path literally. zsh does not word-split a variable, so a path list held in one
   shell variable arrives as a single argument and fails.

   Convention: `[BUILD-XXXX] <type>: <subject>`, where type is `feat`, `fix`, `test`,
   `docs`, or `chore`. `-s` adds the sign-off, `-S` GPG-signs. Add `Co-Authored-By: Claude`
   with no email address. Before every commit, confirm the message's issue key equals the
   branch's issue key.

4. Verify what actually landed, on which branch:

```bash
git -C "$WT" show --name-only --format='' HEAD
git -C "$WT" branch --show-current
```

5. Push to the **fork**, by explicit refspec, so no checkout is needed:

```bash
git -C "$WT" push <fork-remote> "BUILD-XXXX-<slug>:BUILD-XXXX-<slug>"
```

   Never push to `origin`. Never plain force-push: use `--force-with-lease`, and first
   preserve the fork's existing tip as a tag and **push the tag before the branch**, so the
   old tip is recoverable by anyone, not just locally:

```bash
git -C "$WT" tag "archive/<fork-remote>-old-BUILD-XXXX-<slug>" <fork-remote>/BUILD-XXXX-<slug>
git -C "$WT" push <fork-remote> "archive/<fork-remote>-old-BUILD-XXXX-<slug>"
git -C "$WT" push --force-with-lease <fork-remote> "BUILD-XXXX-<slug>:BUILD-XXXX-<slug>"
```

## Phase 7: Update Jira

Jira is the single source of truth. Record the change there directly.

### Evidence gate — no exceptions

Whether you may claim the work is tested is gated on evidence:

- Claim it tested (in the comment, and when transitioning the issue toward a review/done
  state) only if `<Designs Directory>/test-results/BUILD-XXXX-results.md` exists and
  contains (a) the exact test commands, (b) pasted raw output, (c) exit code 0, (d) the
  branch HEAD SHA tested, and — for cluster-observable behaviour — (e) cluster evidence
  such as `oc` output or BuildRun status.
- Compare the SHA recorded in the results file against the current tip, and fail the gate
  when they differ — a stale results file must not vouch for an untested commit:

```bash
recorded="$(grep -oiE '[0-9a-f]{7,40}' "<Designs Directory>/test-results/BUILD-XXXX-results.md" | tail -1)"
current="$(git -C "$WT" rev-parse HEAD)"
[ -n "$recorded" ] && [ "$current" = "$recorded" ] || { echo "results file SHA ($recorded) != current tip ($current) — treat as untested"; }
```

- If any element above is missing, or the SHAs differ, say "implemented, evidence pending"
  in the comment and leave the issue in progress rather than moving it to review/done.
- Never claim tested on the strength of a narrative.

### Jira write

Every action below mutates Jira. Show the user the exact list — comment text, attachment,
status transition, and story points — and get one explicit approval before running any of
them. Skip any the user declines.

- Post a comment summarising the change and the test results, including the branch
  (`<fork-remote>:BUILD-XXXX-<slug> (<repo-name>)`, one line per repo when the change spans
  several). Pass the approved text through stdin — never interpolate it into the shell
  command, where backticks or `$(...)` in the text would be executed instead of posted:

```bash
printf '%s\n' "$APPROVED_COMMENT" | jira issue comment add BUILD-XXXX --template - --no-input
```

- Attach the updated design doc. Reference it by **filename** in any comment; an absolute
  local path discloses the author's home directory and is useless to everyone else.
- Transition the issue to match the evidence gate above.
- Write and verify story points via jira-cli (`customfield_10028`). Raw REST reads return
  obfuscated data.
- Read back with `jira issue view BUILD-XXXX` and confirm status and points before printing
  the banner.

### Summary banner

```
IMPLEMENTATION COMPLETE: BUILD-XXXX
====================================
Repos modified:
  - <repo>: <fork-remote>:BUILD-XXXX-<slug> (pushed to fork)

Tests:
  - Unit:    X/Y passed — results: test-results/BUILD-XXXX-results.md @ <HEAD SHA>
  - Cluster: <PASS/FAIL/N-A> — evidence: <section of the results file>

Jira:    comment added, attachment replaced, status <state>, points set and read back
PR:      <not created yet / link>
```

A banner claim without a matching results file is prohibited. Any test name cited must exist
in the branch diff or on main — verify with
`git -C "$WT" diff --no-ext-diff origin/main...HEAD -- '*_test.go'`.

## Phase 8: Create the PR

On user request, once the branch is pushed to the fork.

```bash
FORK_OWNER="$(git -C "$WT" remote get-url <fork-remote> \
  | sed -E 's#^(git@[^:]+:|https://[^/]+/)([^/]+)/.*#\2#')"

gh pr create --repo <upstream-org>/<repo-name> \
  --head "$FORK_OWNER:BUILD-XXXX-<slug>" \
  --base main \
  --title "[BUILD-XXXX] <title>" \
  --body-file <path to a file holding the approved body>
```

Use `--body-file`, not an inline heredoc, so backticks and `$(...)` in the body are not
executed by the shell.

The body states what the change does and why, in terms a reviewer with no prior context can
follow. It covers the change, the testing evidence, and a Jira link. Do not narrate the
project's internal history.

Then, with one explicit user approval covering all of it, transition the issue to reflect
that the PR is open and add the PR link as a Jira remote link and comment.

## Completion Status
